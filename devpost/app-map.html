Room to Speak — App Map

A one-page guide to where things live in this app, so the next change starts in the right file. Snapshot of commit dc28c54; the code can drift after this.

The app in three pieces

The browser app

Setup (caregiver) and Speak (him) screens, the one saved scene, and the device voice. src/

The detect helper

Receives the room photo once, asks Gemini, checks the answer. Keeps the API key off the device. api/detect.ts

Gemini

Finds up to 8 objects worth talking about and writes a first-person phrase for each. Prompt in shared/prompt.ts.

One action, end to end: he taps the kettle

Reference route (3 stops)

Not toured interactively — open these in your editor when you want to follow the tap yourself.

  1. src/components/PhotoStage.tsx → search function up. A tap counts on release, inside the same ring it started in; a second finger cancels it. That rule protects him from palm and knuckle touches.
  2. src/geometry.ts → nearestRing. Turns the tap position into a spot: among the rings the tap falls inside, the nearest center wins. Tested in tests/geometry.test.ts.
  3. src/speech.ts → useSpeaker / speak. Cancels any phrase in progress, picks an id-ID voice, and reports which spot is speaking so the ring can pulse.

To change this, start here

The words on the core row (Ya / Tidak / Tolong / Sakit / Toilet)

src/copy.ts → CORE_WORDS. label is the button, phrase is what gets spoken.

What the AI looks for, or how the phrases sound

shared/prompt.ts → buildPrompt. The answer format is RESPONSE_SCHEMA; answers are checked in shared/validate.ts.

Which AI models are tried, in what order, and how long each gets

api/detect.ts → ATTEMPTS (Gemini → Gemini Flash-Lite → DeepSeek, each with its own ms), TOTAL_BUDGET_MS, loop in findSpots.

Ring size and placement

src/scene.ts → boxToSpot (box → ring) and separateSpots (nudges overlapping rings apart). Look in src/styles.css → .ring for how they're drawn.

Any screen text in Indonesian or English

src/copy.ts → COPY.id / COPY.en.

A practice to reuse

Name the failure modes in the plan, then prove them against the real service. devpost/spec.md listed "Gemini busy or offline" as a failure mode with a planned fallback. The unit tests passed, but a final run of e2e/slice1-detect.mjs against the real API still failed: a timeout threw an error instead of returning a status, so it skipped the retry loop entirely. The fix (commit 863498a, now findSpots in api/detect.ts) treats timeouts like overload and falls back across models within one time budget.

On the next project: write the two or three realistic failures into the spec, and keep one end-to-end check that runs against the real dependency — mocks only prove the paths you already imagined.
